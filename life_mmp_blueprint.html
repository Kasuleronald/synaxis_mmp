Section 01

Understanding

The platform is now named Life MMP — A Ministry Management Platform. The rename replaces "ZOE," which collided with the name of one of the actual churches lining up to join the platform (a church literally called Zoe would have shared its name with the software running it). "Life" keeps the original concept — growth, discipleship, vitality — without claiming a name a real tenant already owns.

It is, explicitly, a multi-tenant SaaS platform, not a single church's system that might one day host others. A platform team creates churches as tenants; each church's admin runs their own branches, staff, and giving independently, with data fully isolated from every other tenant. Tenancy is core infrastructure from day one, not a later retrofit.

Three realities shape the architecture beyond the module list itself:

  • No source system exists. Every onboarding church arrives with data trapped in spreadsheets, PDFs, and Word documents, each in whatever format that church happens to use. Getting that into Life MMP cleanly is a first-class product problem — the AI-assisted import module in Section 7.
  • Payments are already solved per church. Churches already hold mobile money merchant codes. Life MMP's job is a thin, per-tenant integration layer, not a payment processor of its own (Section 8) — and by your direction, that integration is built last, once everything churches actually enter data into is solid.
  • Production hosting arrives partway through the build. Oracle Cloud is provisioned near the end of the 90 days, not Week 1. The build is sequenced local-first from day one so that arrival is a cutover, not an architecture change — see Sections 4 and 10.
90 days, not 30

The extra runway changes what's realistic. Fellowships, discipleship classes, directorate hierarchy, and a genuine offline-sync engine move back into the core build instead of being deferred — see the rebalanced scope in Section 2. MTN MoMo moves the other direction, to the very end, per your direction that it's low-urgency since every church already collects money its own way today.

Section 05

Database — what changes

organizations is real, not symbolic
Every tenant-scoped table carries a non-null organization_id with an enforced Postgres RLS policy. The row also carries display_name, logo_url, and theme — a church's own identity and chosen theme, not the platform's, is what its users see.
import_staging
Rows extracted from an upload land here first — source_file_id, extracted_fields (JSONB), confidence, status, reviewed_by. Nothing here is a real member/giving record until approved.
payment_providers
Per-org row: provider_type, merchant_code, encrypted API credentials, environment, webhook_secret — table exists Day 90, populated once MTN MoMo ships in fast-follow.
branches
What the brief called campuses — one org, many branches, unchanged modeling.

Section 07

AI-assisted data import

AI does extraction, never decision — a human always confirms before anything becomes a real record. Unchanged from the previous draft. What's new here is format flexibility: the pilot church's Excel is the first real test case, but the import pipeline is built to handle whatever a church actually has, not a format they're required to match.

  1. Upload. Excel, CSV, PDF, or Word, tagged with what it is (member list, attendance register, giving log).
  2. Deterministic pass first, with fuzzy header matching. The column mapper recognizes common variants of a field automatically — "Name" / "Full Name" / "Member Name" all map to the same target field — instead of requiring an exact header match. This handles most real-world spreadsheets, including ones with no relation to any template, without an AI call.
  3. Gemini pass for the messy remainder. PDFs, Word documents, and spreadsheets without usable headers go to Gemini as extracted text, with a structured-output prompt asking for named fields and a confidence score per field.
  4. Staging, not the real table. Every extracted row lands in import_staging, flagged for low confidence and likely duplicates.
  5. Human review, then commit. A staff member fixes, dedupes, and approves; approved rows write to the real schema in one transaction with an audit log entry.
Starter template — optional, not required

Alongside "bring whatever you have," Life MMP offers a downloadable starter spreadsheet with sensible columns (name, phone, gender, DOB, branch, department) for churches with no existing records, or who'd rather retype into a clean sheet than scan a paper register. It's a fast path, not a gate — the fuzzy mapper and Gemini extraction both work with or without it. Confirming you want this built in Section 18.

Section 10

Offline & sync — back in core scope

The previous draft pushed the full sync engine to fast-follow to protect a 30-day launch. With 90 days, and a build that's local-first by necessity (Oracle Cloud isn't live until late in the timeline), the full engine belongs in the core build — it's being built anyway as the primary way the app talks to its own data.

Local-first as dev strategy
The client reads and writes IndexedDB directly from Sprint 1. A background sync worker drains an outbox against the API — which, until Sprint 6, is a local/interim server, and after Sprint 6, is Oracle Cloud. The app never notices the difference.
What stays online-only
Giving writes are never queued offline, AI import commits require a live connection to call Gemini — both unchanged from the original design, for the same integrity reasons.

Section 11

UI / UX & theming

Sidebar grouped by domain, ⌘K global search, role-configured dashboards. Two identity layers stack on top of that shell: a platform-level theme the user picks, and a church-level logo and name the Org Admin sets (Section 5). They're independent — a church's brand doesn't change when a user picks a different theme, and a theme looks the same across every church that uses it.

Five themes

All five ship Day 90. Each is a light/dark token pair, not a single fixed color — respecting whichever mode the user's device is in.

Convenient coincidence: the dark-background mark's green-to-gold gradient already reads as Growth, and the light-background mark's purple-magenta already reads as Regal — those two need no recoloring. Heritage, Ember, and Slate would each want their own gradient pass if you want a themed mark per theme, using the accents above.

For the in-app header itself, recommend a single flat, single-color (not gradient) outline version of the mark rendered with currentColor — it then automatically matches whichever of the 5 themes × 2 modes a user has picked, without exporting 10 logo files. Save the full gradient versions for the marketing/landing page, where one fixed brand color is the point.

Tenant identity in the header. Every logged-in user sees their own church's logo and name in the top bar — resolved from organizations.display_name/logo_url at session start and cached with the offline shell. A text-only wordmark fallback covers churches that haven't uploaded a logo yet.

Events surface "upcoming" prominently on the dashboard and in a lightweight calendar view — one of the first things a branch admin uses, so it belongs on the main dashboard, not buried in a module. The Import Center gets its own visual state machine — Uploaded → Extracting → Ready for Review → Committed.

Section 12

API

Versioned REST (/api/v1/{domain}), every route resolving organization_id from the authenticated session — never from a client-supplied parameter. Domains: members, visitors, attendance, fellowships, discipleship, giving, events, import, payments, reports, sync. The contract is identical whether the server is a local Docker container (Weeks 1–~11) or Oracle Cloud (from Sprint 6) — that's what makes the cutover a deploy, not a rewrite.

Security

Tenant isolation is a security control
Row-level security by organization_id, tested directly — not assumed from application code being correct.
Secrets never touch the client
Gemini key and mobile money API credentials live server-side only, encrypted at rest.
Platform Admin break-glass
Any support access to tenant data is logged and time-boxed — see Section 6.
Standard hardening
Session auth, Argon2 hashing, audit logging, rate limiting, encryption at rest — unchanged from the original draft.
Section 14

Reporting

Scheduled rollups feed the dashboard rather than live aggregation across every record on every page load. Day 90 ships member count, attendance trend, giving trend, and follow-up completion as computed daily rollups; deeper drill-down reporting is fast-follow.

Section 16

MVP definition

Day 90 is done when: a Platform Administrator creates a new church and appoints its admin; the admin sets a theme, uploads the church logo, creates two branches, and invites a finance officer, a directorate head, and a fellowship leader; the admin uploads the church's real membership Excel — in whatever format it already is — reviews the AI-assisted extraction, and commits clean member records; an usher checks in Sunday attendance on a budget phone with a weak connection and it queues, then syncs correctly with a visible status once back online; a fellowship leader records their own cell group's attendance; a discipleship class tracks who's enrolled and who attended; giving is recorded manually against categories; and by Monday morning the admin's dashboard — served from church.scholarsas.com — shows member count, this week's attendance trend, and this week's giving.
